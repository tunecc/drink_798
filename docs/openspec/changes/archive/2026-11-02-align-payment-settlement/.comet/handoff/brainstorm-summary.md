## 确认的技术方案（用户已于 2026-11-02 Step 1c 确认）

继承 Open 阶段已确认的 5 项决策（D1 删除静默回退 / D2 错误码映射并入纯函数提示助手 / D3 有界轮询拉账单 / D4 余额接口用现有 token，被拒时仅对该两接口补 `ApplicationType: 1,1` / D5 余额区为可空状态按 home-page-ui 规则渲染），并做一项经证据确认的细化：

- **D3 细化（已确认）**：账单获取为**列表→详情两步**。结算后有界轮询 `GET /bill/lst-owner?page=0&size=20`（过滤 `type=91`/`status=3`/`cata=6`、当前设备、时间 ≥ 会话开始，取最新一条）找到新账单 id，再 `GET /bill/view-full?id=<id>`（响应 `data.bill`）获取积分抵扣明细。依据：参照项目 `IlifeApi.java:293-298,330-332` 与 `ConfigActivity.kt:325` 注释（"列表仅提供最近 20 笔订单；逐笔读详情才能包含积分抵扣"）。列表不含 `promo`，只报列表会把积分全额抵扣的账单误报为 ¥0，因此详情在轮询窗口内拉不到时静默结束，不报错误金额。design.md 开放问题 #1（端点路径）就此关闭；开放问题 #2（个别设备账单形状偏差）保留为构建期真机验证，解析回退为只报 payment 总额时须同时满足"不会把 0 元误报为全额"的前提，否则同样静默。
